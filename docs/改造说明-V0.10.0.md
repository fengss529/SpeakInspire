## 一、数据层：DB v3 → v4

### 1.1 变化总览

| 表 | 变化 | 理由 |
|---|---|---|
| `note` | **不动** | 已经是独立资源 |
| `article` | 去外键；`noteId` → `sourceNoteId`（可空、普通列）；新增 `sourceText` | Q8：生成后独立存活，但仍能看到出处 |
| `script` | 去外键（原本指 `article`）；`articleId` → `sourceArticleId`（可空、普通列）；新增 `sourceTitle` | 选题独立；`sourceTitle` 让选题脱离文章后仍能自报家门 |
| `trashed` | 主键 `noteId` → `id`；新增 `resourceType` / `resourceId` | Q9：能装三种资源 |
| `deepening` | **不动**（仍 CASCADE 挂 `note`） | 见 1.4 |
| `sprout` | **不动**（仍 CASCADE 挂 `note`） | 见 1.4 |
| `provider` | 不动 | 与本次无关 |

### 1.2 新表结构

```kotlin
// article：去掉 foreignKeys，加来源快照
@Entity(
    tableName = "article",
    indices = [Index("sourceNoteId")],   // 普通索引，不是外键
)
data class ArticleEntity(
    @PrimaryKey val id: String,
    /** 出处记录。**无外键**，记录被删后此列悬空，UI 显示「原始记录已删除」 */
    val sourceNoteId: String?,
    /** 生成那一刻的记录原文快照。记录删了也还在 */
    val sourceText: String,
    val title: String,
    val paragraphsJson: String,
    val writtenAt: Long,
    val edited: Boolean,
)

// script：同样去外键
@Entity(
    tableName = "script",
    indices = [Index("sourceArticleId")],
)
data class ScriptEntity(
    @PrimaryKey val id: String,
    /** 出处文章。无外键 */
    val sourceArticleId: String?,
    /** 文章标题快照——选题独立后仍要知道自己从哪来 */
    val sourceTitle: String,
    val angle: String,
    val rationale: String,
    val sectionsJson: String,
    val createdAt: Long,
    val shotAt: Long?,
    /** 搁置：先不拍。**不再等于「移回思考库」**，它就是选题自己的一个状态 */
    val parked: Boolean,
    val note: String,
)

// trashed：从「只能装记录」扩成「能装三种资源」
@Entity(
    tableName = "trashed",
    indices = [Index(value = ["resourceType", "resourceId"], unique = true)],
)
data class TrashedEntity(
    @PrimaryKey val id: String,
    /** "note" / "article" / "script" */
    val resourceType: String,
    val resourceId: String,
    val deletedAt: Long,
    /** 恢复时按原排序插回，记录用 */
    val originalIndex: Int,
)
```

### 1.3 迁移 SQL（v3 → v4）

**顺序不能换。** SQLite 的 `DROP TABLE` 在开启外键时会触发级联动作，所以必须先建好没有外键的 `script`，再动 `article`，否则文章下的选题会被连带删掉——这正是不想再发生一次的事故。

```sql
-- ① 先重建 script（去掉指向 article 的外键）
CREATE TABLE script_new (
    id TEXT NOT NULL PRIMARY KEY,
    sourceArticleId TEXT,
    sourceTitle TEXT NOT NULL DEFAULT '',
    angle TEXT NOT NULL,
    rationale TEXT NOT NULL,
    sectionsJson TEXT NOT NULL,
    createdAt INTEGER NOT NULL,
    shotAt INTEGER,
    parked INTEGER NOT NULL,
    note TEXT NOT NULL
);

INSERT INTO script_new (id, sourceArticleId, sourceTitle, angle, rationale,
                        sectionsJson, createdAt, shotAt, parked, note)
SELECT s.id, s.articleId, COALESCE(a.title, ''), s.angle, s.rationale,
       s.sectionsJson, s.createdAt, s.shotAt, s.parked, s.note
FROM script s LEFT JOIN article a ON a.id = s.articleId;

DROP TABLE script;
ALTER TABLE script_new RENAME TO script;
CREATE INDEX index_script_sourceArticleId ON script(sourceArticleId);

-- ② 再重建 article（此时已无子表指向它）
CREATE TABLE article_new (
    id TEXT NOT NULL PRIMARY KEY,
    sourceNoteId TEXT,
    sourceText TEXT NOT NULL DEFAULT '',
    title TEXT NOT NULL,
    paragraphsJson TEXT NOT NULL,
    writtenAt INTEGER NOT NULL,
    edited INTEGER NOT NULL
);

INSERT INTO article_new (id, sourceNoteId, sourceText, title, paragraphsJson, writtenAt, edited)
SELECT a.id, a.noteId, COALESCE(n.body, ''), a.title, a.paragraphsJson, a.writtenAt, a.edited
FROM article a LEFT JOIN note n ON n.id = a.noteId;

DROP TABLE article;
ALTER TABLE article_new RENAME TO article;
CREATE INDEX index_article_sourceNoteId ON article(sourceNoteId);

-- ③ 重建 trashed（旧记录全部标为 note 类型）
CREATE TABLE trashed_new (
    id TEXT NOT NULL PRIMARY KEY,
    resourceType TEXT NOT NULL,
    resourceId TEXT NOT NULL,
    deletedAt INTEGER NOT NULL,
    originalIndex INTEGER NOT NULL
);

INSERT INTO trashed_new (id, resourceType, resourceId, deletedAt, originalIndex)
SELECT 'tr_note_' || noteId, 'note', noteId, deletedAt, originalIndex FROM trashed;

DROP TABLE trashed;
ALTER TABLE trashed_new RENAME TO trashed;
CREATE UNIQUE INDEX index_trashed_resourceType_resourceId
    ON trashed(resourceType, resourceId);
```

**验证标准**（在模拟器上用现有的 4 条记录 + 1 篇文章做）：

1. 迁移前记录 `count(note)`、`count(article)`、`count(script)`、`count(deepening)`、`count(sprout)`
2. 迁移后五个数字**全部一致**
3. `article.sourceText` 等于对应 `note.body`，非空
4. `script.sourceTitle` 等于对应 `article.title`
5. 应用启动不抛 `Room cannot verify the data integrity`（identity hash 校验）
6. `PRAGMA foreign_key_check` 返回空

> 第 5 条最容易踩：Room 的 identity hash 是根据实体定义编译期算出来的，迁移 SQL 只要少一个索引、字段类型写错（`INTEGER` vs `TEXT`）、`NOT NULL` 漏写，就会在启动时直接崩。**必须真机验证，不能只靠编译通过。**

### 1.4 为什么 `deepening` / `sprout` 保持 CASCADE

`article` 和 `script` 是**衍生资源**——它们是那次思考的产物，产物本身能独立活下去。
`deepening` 和 `sprout` 是**附着物**——追问的每一轮都在谈这条记录里的那句话，发芽的种子直接引用记录原文。记录没了，它们失去锚点，留着只是一堆无主的问答。

所以：删记录 → 连带删追问和发芽；**但不删文章，也不删选题**。

> 这条能不能改：能，但要先想清楚「一条没有原始记录的发芽报告」给用户看什么。

## 二、领域层：把 `IdeaView` 拆成三个

### 2.1 现状的问题

`IdeaView(note, deepening, article, scripts, sprouts)` 是一条链的快照，`derive()` 在这条链上算 8 个状态。它假设「记录 → 追问 → 文章 → 选题」是一条流水线，所以：
- 选题搁置会把**文章**标成「先留着」
- 记录有没有被拍摄过，会反过来影响**记录**的状态（`STALE`）
- 思考 tab 的条目本质是「有文章的 note」

这就是「捆绑成一个对象」。拆掉。

### 2.2 拆完的三个视图

```kotlin
/** 记录 tab：一条记录 + 它自己的附着物。生命周期一致（CASCADE） */
data class NoteView(
    val note: Note,
    val deepening: Deepening?,
    val sprouts: List<Sprout>,
    /** 由它生成的文章 id（可能多条？不，见 2.4）。只持 id，不持对象 */
    val articleId: String?,
    /** 从它派生出了新记录 */
    val hasChild: Boolean,
) {
    val latestSprout: Sprout? get() = sprouts.maxByOrNull { it.createdAt }
    val sproutCount: Int get() = sprouts.size
}

/** 思考 tab：文章独立成条。topics 是查询出来的关联，不是持有 */
data class ArticleView(
    val article: Article,
    val topicCount: Int,
) {
    /** 出处记录还在不在。false 时 UI 显示「原始记录已删除」 */
    val hasSource: Boolean get() = article.sourceNoteId != null
}

/** 选题 tab：选题独立成条 */
data class TopicView(val script: Script) {
    val state: TopicState get() = when {
        script.shotAt != null -> TopicState.SHOT
        script.parked -> TopicState.PARKED
        else -> TopicState.TODO
    }
}
```

### 2.3 三个独立的状态机，取代原来的 8 状态

```kotlin
enum class NoteState(val label: String) {
    RECORD("记录"),        // 没追问没文章
    ONGOING("深化中"),      // 有未收尾的追问
    DEEPENED("已深化"),     // 追问收尾了但还没成文
    COMPOSED("已成文"),     // 有文章
    DERIVED("已派生"),      // 从它派生出了新记录
}

enum class TopicState(val label: String) {
    TODO("待开拍"),
    SHOT("已拍摄"),
    PARKED("搁置"),
}

// 文章不需要状态。列表按 writtenAt 倒序即可
```

**关键变化**：`PARKED` 从「文章的状态」变成「选题的状态」。`STALE` 改名 `DERIVED`，且**不再依赖是否拍摄**——记录只关心「我派生过没有」。

> 这条能不能改：状态命名可以调，但**状态不能再跨资源**。选题拍没拍，不该改变记录上显示什么。

### 2.4 一条记录能有几篇文章

结论：**仍然最多一篇**（`article.id = "a_$noteId"` 的约定保留）。

理由：多篇会让「记录页那一个『看这篇文章』按钮指向哪篇」变得没有答案。想要第二篇，用「接着这句记一条」派生新记录——这条路径已经存在，且语义更清楚。

代码上：`ArticleView` 与 `NoteView` 通过 `sourceNoteId` 一对多查询，但保存时仍是 upsert，实际不会出现两条。

> 这条能不能改：如果以后要支持一篇记录写多稿，先解决记录页入口的问题。

## 三、导航与操作矩阵

### 3.1 三个 tab 各自的完整能力

| 能力 | 记录 tab | 思考 tab | 选题 tab |
|---|---|---|---|
| 新建 | ＋按钮 | — | — |
| 列表排序 | `createdAt` 倒序 | `writtenAt` 倒序 | 待拍在前、已拍沉底、搁置沉底 |
| 打开 | 详情页 | 文章页 | 骨架页 |
| 编辑 | ✅ 标题+正文 | ✅ 标题+正文（`updateArticleContent` 已有） | ✅ 镜头备注 |
| 删除 | ✅ ⋮ → 删除 | ✅ ⋮ → 删除 | ✅ ⋮ → 删除 |
| 追问 | ✅ | ✅（回头再聊） | — |
| 发芽 | ✅ | — | — |
| 成文 | ✅ | — | — |
| 转选题 | — | ✅ | — |
| 标记已拍 / 撤销 | — | — | ✅ 右滑 / 撤销条 |
| 搁置 / 取消搁置 | — | — | ✅ 左滑 |
| 导出 | 单条 md → 分享面板 | — | — |

**空白处就是设计**：思考 tab 不该能追问（它在记录页），选题 tab 不该能编辑正文（它只有骨架和备注）。

### 3.2 删除入口

统一用顶栏 `⋮` 菜单，不用手势——因为选题 tab 的左/右滑已经被「搁置 / 标记已拍」占了，再塞删除会更危险。

### 3.3 回收站

- 入口：**设置页 → 你的数据 → 回收站（N）**
- 页面：按 `deletedAt` 倒序，每行显示「类型 · 标题 · 删除时间」，两个动作：恢复 / 彻底删除
- 保留期沿用现状（`purgeExpiredTrash` 那套）

`TrashedEntity` 有三个类型，回收站页面需要按 `resourceType` 分别查标题：
- `note` → `note.title`
- `article` → `article.title`
- `script` → `script.angle`

> 这条能不能改：入口位置可以换（比如记录 tab 顶部），但**不能只做硬删**。文章和选题是模型花钱生成的，误删不可恢复比丢一条随手记疼得多。

## 四、文本选择

### 4.1 实现载体：`BasicTextField(readOnly = true)`

不用 `SelectionContainer`，原因：它**不暴露设置选区的 API**，没法实现「工具栏点一下就扩到整句」。用只读的 `BasicTextField` 可以自己持有 `TextFieldValue`，直接改 `selection`。

封装成一个组件：

```kotlin
// ui/components/SelectableText.kt
@Composable
fun SelectableText(
    text: String,
    style: TextStyle,
    /** 是否在工具栏里提供「选这句」 */
    sentenceAction: Boolean = true,
)
```

内部：
- `BasicTextField(value = TextFieldValue(text), onValueChange = {}, readOnly = true, textStyle = style)`
- 自定义 `TextToolbar` 通过 `CompositionLocalProvider(LocalTextToolbar provides ...)` 注入，在 `showMenu` 里额外插入一项「选这句」
- 点「选这句」时：读当前 `selection.focus` 偏移 → 拿 `TextLayoutResult` → 向两侧扫描句子边界 → 回写 `TextFieldValue.selection = TextRange(start, end)`

句子边界规则（中文为主）：
```
终止符：。！？；…\n
英文句点：后跟空格或行尾才算（避免 3.14、v1.2 被切开）
连续终止符：。！ 这种要一起吃掉，且带走后面的引号 / 右括号
```

### 4.2 用在哪

| 位置 | 需要 |
|---|---|
| 记录详情页正文 | ✅ |
| 追问页：AI 问题、用户每轮回答、原始记录卡 | ✅（当前这一问是流式的，流结束后才可选中） |
| 成文页正文 | ✅ |
| 发芽页：标题、每节 seed / insight / source | ✅ |
| 选题骨架页：段标题、目标、意群短语 | ✅ |
| 列表卡片的两行预览 | ❌ 不要。列表里长按应该留给卡片手势，不是选字 |

### 4.3 「长按选句」的口子留在哪

如果要升级到「长按直接选整句」，在 `SelectableText` 内部拦 `pointerInput`，判断长按 → 换算到字符偏移 → 直接设 selection。**改动只在这一个文件里**，调用方不用动。

## 五、导出

### 5.1 两条路径，语义分开

| 路径 | 入口 | 产物 | 落点 |
|---|---|---|---|
| **全量备份** | 设置 → 你的数据 → 导出全部 | `data.json` + `随手记-全部-时间戳.md` | `Download/随手记/` |
| **单条分享** | 记录详情页顶栏分享图标 | 一个 `.md` | `cacheDir/exports/` → 系统分享面板 |

不做「导出目录选择」。用户要的默认位置就是 Download，多一个选择器只增加一次点击。

### 5.2 JSON 结构

```json
{
  "schemaVersion": 1,
  "app": "随手记",
  "appVersion": "0.10.0",
  "exportedAt": "2026-10-28T09:15:00+08:00",
  "notes": [
    {
      "id": "n_...", "title": "...", "body": "...",
      "createdAt": 1761000000000, "source": "...", "parentId": null,
      "deepenings": [
        { "id": "...", "startedAt": 0, "finishedAt": 0,
          "rounds": [ { "question": "...", "answer": "..." } ] }
      ],
      "sprouts": [
        { "id": "...", "title": "...", "createdAt": 0,
          "sections": [ { "seed": "...", "insight": "...", "source": "..." } ] }
      ]
    }
  ],
  "articles": [
    { "id": "a_...", "sourceNoteId": "n_...", "sourceText": "...",
      "title": "...", "writtenAt": 0, "edited": false,
      "paragraphs": [ { "text": "...", "isMine": true } ] }
  ],
  "topics": [
    { "id": "s_...", "sourceArticleId": "a_...", "sourceTitle": "...",
      "angle": "...", "rationale": "...", "createdAt": 0,
      "shotAt": null, "parked": false, "note": "...",
      "sections": [ { "heading": "...", "goal": "...", "phrases": ["..."], "shotHint": "..." } ] }
  ]
}
```

设计约束（为了下一版能导入）：
- 每类资源都有**自己的 id**，不依赖自增
- 关系靠 id 表达，不靠嵌套位置——虽然 note 里嵌了 `deepenings`/`sprouts`，但它们各自也有 id
- 时间统一毫秒时间戳（整数），不用字符串。`exportedAt` 除外
- **不写派生状态**（`NoteState` 之类），导入时重算

### 5.3 序列化：手写，不引库

现在没有 JSON 库（V0.9.0 删了 moshi）。这里**不加新依赖**，理由：
- 结构是我们自己固定的，不是通用对象序列化
- 解码器已经有了（`JsonScan.kt`），下一版导入直接复用
- 避免再碰一次 ProGuard / KSP 的坑

新增 `data/export/JsonWriter.kt`，约 80 行，提供：
```kotlin
object JsonWriter {
    fun obj(vararg fields: Pair<String, String?>): String   // 值是已编码的片段
    fun str(s: String): String                              // 转义 + 引号
    fun num(n: Long): String
    fun bool(b: Boolean): String
    fun arr(items: List<String>): String
}
```
转义规则：`"` `\` `/` 控制字符 `\b \f \n \r \t`，以及 `< 0x20` 的 `\u00XX`。中文不转义（UTF-8 直出）。

### 5.4 落盘

```kotlin
// API 29+：MediaStore.Downloads，零权限
val values = ContentValues().apply {
    put(MediaStore.Downloads.DISPLAY_NAME, fileName)
    put(MediaStore.Downloads.MIME_TYPE, "application/json")
    put(MediaStore.Downloads.RELATIVE_PATH, "${Environment.DIRECTORY_DOWNLOADS}/随手记")
}
resolver.insert(MediaStore.Downloads.EXTERNAL_CONTENT_URI, values)?.let {
    resolver.openOutputStream(it)?.use { os -> os.write(bytes) }
}
```

API 26–28 分支：`Environment.getExternalStoragePublicDirectory(DIRECTORY_DOWNLOADS)/随手记` + `File.writeBytes`，需要权限：

```xml
<uses-permission
    android:name="android.permission.WRITE_EXTERNAL_STORAGE"
    android:maxSdkVersion="28" />
```
运行时请求（仅 `Build.VERSION.SDK_INT < 29` 时）。拒绝授权 → 提示「请允许写入存储，否则无法导出」并中止，**不要静默失败**。

导出成功后：Snackbar 显示「已导出到 Download/随手记/」+「查看」按钮（`ACTION_VIEW` 打开目录）。

> 这条能不能改：位置固定 Download 是本轮明确决定。若以后要加目录选择，走 SAF `OPEN_DOCUMENT_TREE`，不要用别的。

## 六、追问方式

### 6.2 grill-me 的手法段全文

```
【这一轮用的方法：逐层逼问】
不换话题、不换角度，就盯着他刚才那一句，一层一层往下剥。
每一层只做一件事：把他那句话里没交代清楚的那一点揪出来，问他凭什么。

剥的顺序（不是每次全走，是沿着他答得最虚的那层往下）：
1. 准确的意思是什么？—— 把模糊的词换成他自己的定义
2. 你凭什么这么说？—— 要依据，不接受「感觉」
3. 那这种情况呢？—— 给一个让他说法站不住的边界场景
4. 要是反过来呢？—— 要他自己找反例

对方说「还行」「差不多」「就是那样」「说不上来」时：不接受，也不跳过。
把同一个问题换一个更具体的入口，再问一次。

和「连续追问为什么」的区别：那个是纵向钻因果，这个是横向找漏洞。
你不问「为什么」，你问「具体指什么」「凭什么」「万一不是呢」。

要点：一次只剥一层。剥到他开始自己改口，就停下来问那一处。
```

### 6.3 prompt 可编辑

**存储**：复用现有 `SharedPreferences("probe_settings")`，新增 key `instruction_<methodId>`（为空表示未改过）。不新建表——这是非敏感的本地偏好，和现有 `probe_method` 同类。

**可编辑范围**：只有 `method.instruction`（手法段）。
其余段落（只问不答段、自检段、示例段、【绝对禁止】段、输出格式、轮次）由 `Prompts.probeSystem()` 固定拼接，**界面上以灰字只读展示**，顶部写一句「这段是产品的底线，不能改」。

> 有利的结构事实：禁区段在拼接顺序里位于手法段**之后**，所以即使用户把手法段写乱，后面的硬约束仍能压住。这是允许开放编辑的前提。

**编辑器 UI**：
```
┌─────────────────────────────────────┐
│ 编辑追问手法                          │
│                                     │
│ 你希望它盯着什么问？                    │
│ ┌─────────────────────────────────┐ │
│ │ 先问这句话里的名词具体指什么…        │ │  ← 预填默认手法段
│ └─────────────────────────────────┘ │
│                            [恢复默认] │
│                                     │
│ ───── 以下不可修改 ─────              │
│ 不给结论、不给建议、不给替代方案          │  ← 灰字，只读
│ 不说「你应该」「我建议你」…             │
│ …                                    │
│                                     │
│              [取消]  [保存]           │
└─────────────────────────────────────┘
```

- 保存后：`Toast`「已保存。下一次追问生效，正在聊的不变」
- 改过的在设置列表里标一个圆点
- 「恢复默认」= 删除该 key，二次确认

**参数传递**：`DeepeningContext` 增加 `instructionOverride: String?`，`RealAiService.streamQuestion` 用它替换 `method.instruction`。**不要在 Service 里直接读 SharedPreferences**——否则链路测试没法断言「设置选了什么 → 请求就是什么」。

## 十、风险清单

| 风险 | 后果 | 应对 |
|---|---|---|
| 迁移 SQL 与实体定义不匹配 | 启动直接崩 `Room cannot verify the data integrity` | 模拟器上真实数据验证；`foreign_key_check`；先备份 db |
