# 设计文档：口语训练 App（口语灵感）

> **状态**：设计已定稿，等待实现
> **版本**：v0.4（对应可交互原型）
> **最后更新**：2026-10-14

---

## Problem Statement

用户想提升自己的口语表达能力，尝试过看书、听播客、参加培训，但都没有坚持下来——因为这些方法的反馈周期太长，看完一本书要三个月才知道有没有用，而且反馈是脑子里的感觉，不是身体里的。

他选择的方法是**每天拍一条真人露脸短视频**，这个方法有效，但立刻暴露出一系列工具缺口：

- **想法记了就忘。** 灵感来得快去得也快，没有顺手记的地方，第二天就忘了。
- **想法是模糊的。** 记下来以为自己想清楚了，实际上只是"感觉哪里不对"。让他讲五分钟他会卡住，因为他根本没想清楚为什么。
- **不知道怎么讲。** 即使想清楚了，也不知道怎么组织成一条 30-60 秒的口播视频——开头该说什么、中间怎么铺、结尾怎么收。
- **讲完不知道好不好。** 拍完就结束了，没有任何反馈证明他比昨天强。
- **想不出拍什么。** 每天拍一条这个承诺本身是压力，灵感枯竭时会直接中断整个习惯。

现有工具全都帮不上：备忘录只能存字，AI 聊天工具会直接给答案（想清楚的是 AI 不是他），短视频平台只是发布渠道不产生思考。

**他真正需要的是一个把「模糊想法」变成「想清楚的表达」的强制流程，并且这个流程不能替他想。**

---

## Solution

一个 Android App，工作流是五段：

```
随手记 → AI 抬杠追问 → 写成文章 → 挑选转选题 → 拍摄 → 看统计
```

核心设计原则只有一条：**AI 在不同阶段有不同的权力，且这个权力边界是刻意划定的。**

| 阶段 | AI 能做什么 | AI 不能做什么 | 保护的是什么 |
|---|---|---|---|
| **随手记** | 完全不介入 | 任何介入 | 记录摩擦必须归零 |
| **追问** | 只提问、攻击你的观点 | **不给结论、不给建议、不给替代方案** | 思辨发生的过程 |
| **成文** | 重组、润色、补充缺失的论证和例子 | 不改变你的观点立场 | 成果的表达质量 |
| **转选题** | 拆解成拍摄骨架 | **不写逐字稿** | 练口语而非练朗读 |
| **统计** | 汇总客观数据 | 不做质量评分 | 提供证据而非评价 |

**为什么追问阶段 AI 不能给答案**：用户的目标是提升思辨能力。如果 AI 直接告诉他缺什么，他就变成在接受结论，思辨能力反而退化。追问阶段的 AI 必须像一根刺——专门找他的漏洞、找他的自相矛盾、找他自己没意识到的地方。

**为什么成文阶段 AI 可以补位**：因为这时候思考已经发生了，他的观点已经确定。AI 在这里做的是"表达优化"，不是"代替思考"。两者不冲突——它们保护的对象不同。

**「来源」视图是这个设计的必要补丁**：正因为成文阶段允许 AI 补论证，用户就失去了"判断哪句是我的观点"的能力。所以文章页必须提供逐段来源标注（`你说的` / `AI 补`）。这不是可选的信任功能，而是 (c) 方案的必要配套。

## User Stories

### 记录层

1. 作为想提升口语的人，我想要一个打开就能写字的空白页，以便我能在想法冒出来的 10 秒内记下它。
2. 作为用户，我想要记想法时**不被任何 AI 打断**，以便我不至于因为看到加载动画而分心。
3. 作为用户，我想要标题可以留空，以便我不必为了起个标题而拖延记录。
4. 作为用户，我想要标签是预置的、多选的，不提供自由输入，以便我 3 秒内选完而不是纠结怎么分类。
5. 作为用户，我想要保存后立刻回到列表，以便我不被打断在"保存成功"这种无聊的中间状态里。
6. 作为用户，我想要在想法写到一半时切走 App 也不丢内容，以便我随时可以中途离开。
7. 作为用户，我不想要语音速记，以便我不用对着手机说话（这会让记录变慢且尴尬）。

### 追问层

8. 作为用户，我想要 AI 只问我问题而不给我答案，以便思考必须发生在我这边。
9. 作为用户，我想要每次追问只问**一个**问题，以便我不至于被五个问题砸懵而随便答。
10. 作为用户，我想要 AI 挑战我的观点而不是附和我，以便我发现自己的漏洞。
11. 作为用户，我不想要 AI 说"你说得对""你的观点很好"，以便我保持警觉而不是被哄开心。
12. 作为用户，我想要追问最多 5 轮，以便这件事有明确的终点而不是无限盘问。
13. 作为用户，我想要 AI 提前收尾时明确告诉我"聊透了"，以便我理解它为什么没问满 5 轮。
14. 作为用户，**我不想要看到"还剩 2 轮"这样的倒计时**，以便我不因为赶进度而敷衍回答。
15. 作为用户，我想要打字的时候 AI 问题的动画还没播完，以便我可以边读边写节省时间。
16. 作为用户，我想要点击 AI 的问题气泡能立刻看到完整问题，以便我不必等打字动画。
17. 作为用户，我想要已完成的轮次折叠成一行，以便 5 轮对话不会长到需要滚动很久。
18. 作为用户，我想要折叠行里显示的是**我自己说过的话**，以便我能快速回忆我当时说了什么。
19. 作为用户，我想要每轮的输入框提示语不同（例如第 1 轮"说说当时具体发生了什么"，第 5 轮"这条视频你打算怎么开头"），以便我知道这一轮该往哪个方向想。
20. 作为用户，我想要每轮上方的灰色提示行告诉我"别讲道理，举个具体场景"，以便我不至于写出一堆空话。
21. 作为用户，我想要用 Enter 键直接发送，以便单手操作更快。
22. 作为用户，我想要追问进度点在我**发送之后**才点亮，以便"AI 问完了但我还没答"不会看起来像已完成。
23. 作为用户，我想要中途退出时进度被保存，以便下次能从这一轮接着聊。
24. 作为用户，我想要主动放弃追问时知道进度会保留，以便我不怕点错。

### 成文层

25. 作为用户，我想要追问结束后自动进入成稿，以便我不需要再点一次"生成"。
26. 作为用户，我想要 AI 把我的追问整理成一篇完整的文章，以便我有一个可以反复引用的成果。
27. 作为用户，我想要 AI 补充缺失的论证、反例、数据，以便文章读起来更扎实。
28. 作为用户，**我不想要 AI 改变我的观点立场**，以便这篇文章确实是我的思考。
29. 作为用户，我想要文章语言流畅、结构清晰，以便我愿意读它、引用它。
30. 作为用户，我想要文章可编辑，以便我把 AI 写得不对的地方改掉。
31. 作为用户，我想要编辑后**仍然是同一篇文章**（不产生副本），以便我的思考库不会因为反复修改而膨胀。
32. 作为用户，我想要看到每段是"你说的"还是"AI 补的"，以便我知道这篇文章有多少是我的。
33. 作为用户，我想要一眼看到"你的话 5 段 / AI 补的 3 段"的比例，以便我判断这篇文章靠不靠谱。
34. 作为用户，我想要在文章页能随时切到追问原文，以便我重走一遍当时的思考路径。
35. 作为用户，我想要素材不够时 AI 老实说"写不了"，以便我不拿到一篇注水的文章。
36. 作为用户，我想要在追问轮数太少时**提前**收到预警，以便我不用等生成失败才知道自己聊得不够。

### 思考库层

37. 作为用户，我想要所有成稿文章永久留在一处，以便它们成为可复用的思考资产。
38. 作为用户，我想要文章能被标记为"📹 适合拍"或"📚 先留着"，以便我知道下一篇拍什么。
39. 作为用户，我想要思考库显示每篇的字数和来源，以便我判断质量。
40. 作为用户，我想要统计我思考库的累计字数和本月新增，以便我看到积累。
41. 作为用户，我希望**选题被移走时文章还在**，以便同一篇内容三个月后能换个角度再拍。

### 选题层

42. 作为用户，我想要从思考库里挑选文章转成拍摄选题，以便我不用重新想选题。
43. 作为用户，我想要同一篇文章能拆出**多个不同角度**的选题，以便一篇内容能拍好几次。
44. 作为用户，我想要"换个角度"时弹出几个候选并附一句说明，以便我快速决定。
45. 作为用户，我选择角度时不想看完整的四段骨架，以便我不被信息量淹没而更难决断。
46. 作为用户，我想要候选角度带类型标签（亲历/挑衅/科普/数据/痛点/反常识），以便我一眼分辨讲法差异。
47. 作为用户，我想要文案骨架是**意群短语**（"我提前准备了稿子"）而不是孤立词（"稿子""卡住"），以便我不必费力组句。
48. 作为用户，我想要每段带建议时长，以便我知道节奏。
49. 作为用户，我想要镜头提示用独立的彩色标签而不是混在关键词里的小字，以便拍摄时余光就能看到。
50. 作为用户，我想要镜头提示默认收起，以便我需要时才去看，不干扰阅读骨架。
51. 作为用户，**我明确不要逐字稿**，以便我练的是表达而不是朗读。
52. 作为用户，我想要知道骨架是"提示词不是台词"，以便我理解该怎么用它。
53. 作为用户，我想要在选题详情能跳回原文，以便我记得这条选题从哪来。
54. 作为用户，我想要右滑标记已拍摄，以便单手操作更快。
55. 作为用户，我想要左滑表示"这个角度先不拍"，以便选题不合适时有个出口而不是只能删掉。
56. 作为用户，我想知道左滑**不会删掉文章**，以便我不怕滑。
57. 作为用户，我想要误触后有撤销条，以便我不因为手势失误而丢东西。
58. 作为用户，我想在拍摄文案页只点"保存"而不是"我拍完了"，以便这个按钮职责单一。

### 统计层

59. 作为用户，我想要看到想法的转化漏斗，以便我知道卡在哪一环。
60. 作为用户，我想要漏斗用**全局口径**（每段/累计总数），以便我能横向比较各环节。
61. 作为用户，我想要看到"已追问但还没成文章"的数量，以便我知道自己有多少想法悬在半空。
62. 作为用户，我想要从这条提示直接跳到待处理列表，以便我立刻去处理。
63. 作为用户，我想要看到连续记录天数，以便我维持节律。
64. 作为用户，我想要在选题库顶部看到"今天还没拍"，以便我不漏掉当天的承诺。
65. 作为用户，我想要看到平均追问轮次和 AI 提前收尾次数，以便我了解自己的使用模式。

### 设置层

66. 作为用户，我想要填自己的 API Key，以便我的数据只在我自己的账号里。
67. 作为用户，我想要从下拉里选服务商而不是手填 base_url，以便我不填错。
68. 作为用户，我想要选 DeepSeek 时自动填好一切，以便我只填 Key 就能用。
69. 作为用户，我想要选 MiMo 时默认模型是当前有效的那个，以便不会因为模型下线而报错。
70. 作为用户，我想要有一个"测试连接"按钮，以便我知道自己填对了没。
71. 作为用户，我想要出错时看到**具体的归因**（Key 无效 / 模型名不存在 / 余额不足 / 端点不对），以便我知道该改什么。
72. 作为用户，我想要我的 Key 被加密存储，以便不被轻易提取。

### 跨层

73. 作为用户，我想要底部导航是记录/思考/加号/选题/统计五格，以便最高频的操作（记录）一步可达。
74. 作为用户，我想要加号在正中且视觉最突出，以便我不会犹豫"从哪开始"。
75. 作为用户，我不想要"归档"这个概念，以便我不必学两套"收起来"的逻辑。
76. 作为用户，我想要删除是可恢复的（30 天回收站），以便我敢删。
77. 作为用户，我不想要空状态页 interrupting 主流程，以便界面不啰嗦。
78. 作为用户，我想要默认状态下卡片不显示状态标签，以便视觉噪音小。
79. 作为用户，我想要 App 自己的文案语气和 AI 一致（不迎合、不鼓励过头），以便整个产品不像两个东西拼的。

## Implementation Decisions

### 架构

- **MVVM + Repository + 单向数据流（UDF）**。每个页面遵循 `UiState / UiEvent / UiEffect` 模式。
- **UI 框架：Jetpack Compose**（不用 XML）。声明式 UI 与 StateFlow 天然集成，是当前新项目的事实标准。
- **依赖注入：Hilt**。
- **单 Activity + Navigation Compose**。
- **本地存储：Room**，所有列表查询返回 `Flow`，由 StateFlow 驱动 UI。
- **网络：Retrofit + OkHttp**。

### 导航结构（v0.4 定稿）

底部五格，顺序固定：

```
记录  |  思考  |  [＋]  |  选题  |  统计
```

- 加号占据正中第三位，直径 56px，带浅色主色容器色描边，视觉权重最高。
- 「记录」tab 承担同一条链路的两段：随手记 + 追问。**不拆成两个 tab**——拆开会导致用户记完一条要走到另一个 tab 去追问，这种割裂感正是要消除的。
- 「思考」tab 即思考库（文章资产层）。
- 设置页不在底部导航，从「记录」tab 右上角进入。

### 关键架构决策：note 表不存 status 字段

`note` 只存不可变字段（id、title、body、tags、created_at、parent_note_id），**所有状态在读取时由关联的 deepening / article / script 派生计算**。

原因：如果 note 存 status，那么「锁定后以此为起点新建」会产生状态同步难题——旧 note 变成"已过时"，但它自己并不知道这件事。派生计算消除了这类同步问题。

### 数据模型

| 表 | 字段 | 说明 |
|---|---|---|
| `note` | id, title, body, tags, created_at, parent_note_id | 不可变，无 status |
| `deepening` | id, note_id, status, round_index, messages, started_at, completed_at | status: active / completed / abandoned |
| `article` | id, note_id, deepening_id, content, words, mine_count, shoot_tag, edited_at | 永久留存 |
| `script` | id, article_id, outline, notes, angle, shot, shot_date, parked | **article : script = 1 : N** |
| `config` | provider, base_url, api_key, model, thinking_disabled | 单行 |

`article : script` 是 1:N，这是"文章是资产、选题是拍摄计划"的直接体现。同一篇文章可从不同角度派生多条选题，原选题保留。

### 派生状态机（8 个，互斥，按优先级判定）

```
1. 已拍摄      script.shot == true
2. 已过时      存在 child_note 且其状态 ∈ {追问中, 待成文, 已成文, 已成选题}
3. 已成选题    存在 script
4. 已成文章    article 存在 且 deepening.status == completed
5. 待成文      deepening.status == completed 且无 article
6. 追问中      deepening.status == active
7. 待深化      无 deepening 记录
8. 追问已放弃  deepening.status == abandoned
```

优先级从高到低判定。例如一条 note 既已拍摄又有 child_note，展示为"已拍摄"。

### AI 权力分阶段（核心设计）

三个提示词场景，权力边界完全不同：

**追问阶段**（自然语言输出，不用 JSON）
```
规则：
1. 只提问，永远不给结论、不给建议、不给替代方案
2. 每轮只问一个开放式问题，禁止二选一
3. 攻击用户的观点：找漏洞、找矛盾、找他没想清楚的地方
4. 不说"你说得对""你的观点很好"
5. 若用户的回答里出现了他自己没意识到的判断，指出这一点然后追问
6. 最多 5 轮。用户已想透时主动收尾
```

**成文阶段**（强制 JSON 输出）
```
要求：
1. 观点必须全部来自用户的回答；可以补充论证、反例、数据
2. 允许调整措辞让语言更优美，但不改变用户的观点立场
3. 若素材不足以支撑 300 字，content 返回空字符串
4. 文章要有清晰逻辑线，不写成流水账
返回 JSON：{title, content, word_count}
```

**转选题阶段**（强制 JSON 输出）
```
要求：
1. 每条选题给出独特切入角度，同一文章可有多条
2. 骨架用意群短语而非孤立关键词（"我提前准备了稿子" 而非 "稿子"）
3. 每段标建议时长，总时长 30-60 秒
4. 给出镜头提示（停顿/看镜头/手势/重音）
5. 不写逐字稿
返回 JSON：{angles:[{hook, core, why}], outlines:[...]}
```

### 「来源」视图设计

文章页右上角入口，切换后展示：

- **顶部占比卡**：双数字对比（你的话 N 段 / AI 补的 M 段）+ 横向占比条
- **逐段标注**：每段左上角贴标签 `你说的`（绿色系）或 `AI 补`（琥珀色系）
- **下方追问原文**：完整的气泡流，可折叠
- **底部警告**：AI 补的段落通常更规整更书面，长期不看会不自觉模仿那种腔调——这正是「练口语」变成「练朗读」的开始

数据支撑：`article.mine_count` 字段记录属于用户的段落数。

### 追问对话页的三个缓解设计

5 轮对话的完整内容约 1000-1400px，是可视区的 2-2.6 倍。三个机制解决：

| 机制 | 做法 | 效果 |
|---|---|---|
| 历史轮次折叠 | 已完成轮次折叠为一行摘要，显示**用户原话前 24 字** | 1000-1400px → 约 620px |
| 输入框不锁 | 打字动画期间输入框可用，仅发送按钮禁用 | 每轮感知延迟从「AI 3s + 从零打字 60s」变为「边读边打」 |
| 动画可跳过 | 点击气泡立即全文显示 | 用户自主控制节奏 |

**折叠摘要必须显示用户原话，不能是 AI 的总结**——否则折叠功能本身就成了补位式 AI，破坏追问阶段的原则。

### 轮次进度指示器

- 5 个进度点 + 2px 线性进度条
- 已完成 = 主色实心 + 对勾 | 当前轮 = 主色实心 + 呼吸脉冲 | 未到 = 空心圆
- **点亮时机：用户点击发送之后**，不是 AI 问完时点亮。AI 问完但没回答 = 该轮未完成。
- 文案措辞：第 1-4 轮 `第 N 轮 · 最多 5 轮`；第 5 轮 `最后一轮`；提前收尾 `AI 判断这里已经聊透了 · N 轮`
- **禁止「还剩 N 轮」**：倒计时制造"赶紧冲完"动机，用户会敷衍作答，与追问阶段的原则直接冲突。

### 文案骨架设计

4 段结构，每段包含：

| 元素 | 内容 |
|---|---|
| 段标题 + 建议时长 | 如 `① 开场钩子 5 秒` |
| 写作目标 | `这段要讲清楚：制造"你也这样"的认同` |
| 意群短语 | 带语法的半句，如 `我提前准备了稿子` / `但张嘴就卡住了` |
| 镜头提示 | 独立彩色标签，默认收起 |

镜头提示 token 与每段上限：

| 图标 | 标签 | 每段上限 |
|---|---|---|
| ⏸ | 停顿 | 1 |
| 👁 | 看镜头 | 1 |
| ✋ | 手势 | 0-2 |
| ⏱ | 加速 | 0-1 |
| 📌 | 重音 | 0-1 |
| 🔁 | 重复 | 1（仅收尾段） |

**关键词必须用意群短语而非孤立词**：孤立词（"稿子""卡住"）对"组句本身就很困难"的用户认知负荷过高，等于把表达训练变成了组句训练。

### 换角度交互

- 底部按钮触发，弹出 3 个候选
- 每个候选：**标题 + 一句话说明 + 类型标签**（亲历/挑衅/科普/数据/痛点/反常识）
- 不在选择时展示完整骨架——选角度时凭的是"我有没有兴趣讲"，看完四段骨架反而更难决断，而且手机上塞不下三套完整骨架
- 选中后立即替换第 1 段的写作目标，完整骨架在详情页看

### 手势设计

| 手势 | 动作 | 语义 |
|---|---|---|
| 右滑 | 标记已拍摄 | 拍摄状态**完全**由右滑产生 |
| 左滑 | 移回思考库 | "这个角度先不拍"，**不是删除**——文章本身没错 |

两者都弹确认框（因为是滑动操作，误触率高），确认后 7 秒撤销条。

**拍摄状态与文案保存职责分离**：详情页底部按钮是「保存」，只管文案编辑，不改变拍摄状态。这个分离的代价是统计可能滞后——需要在统计页做「有 N 条选题已开拍但未标记」的提醒补上。

左滑的动作语义必须补齐：上一版左右滑都标记已拍摄，本版只定义右滑，左滑若无语义就会成为无意义手势，用户滑一次没反应就不再试了。

### 服务商配置

| 默认模型 | `deepseek-flash` | `mimo-v2.6-pro` |

**不进第一批的服务商及原因**：

| 服务商 | 排除原因 |
|---|---|
| 百度千帆 | key 是 `bce-v3/ALTAK/xxx` 三段式，与"填 API Key"的直觉不符 |

**三个必须处理的坑**：

1. **MiMo 模型名时效**：`mimo-v2.5-pro` 已于 2026-10-21 下线，之后自动转发 V2.6。默认值必须写 `mimo-v2.6-pro`。
2. **思考模式默认状态相反**：MiMo 的 `thinking` 默认 `enabled`，需显式关闭；DeepSeek 则是 flash 模型天然无思考。设置页需分别说明——两家的心智模型不同。
3. **SSE keep-alive**：解析器必须容忍 `: keep-alive` 注释帧与空帧，否则解析失败。MiMo 官方未说明但实践中同样需要容错。防御写法：`if (!chunk.choices) continue`。

### 统一调用层

两家服务商统一走 OpenAI 兼容格式，差异只在思考模式控制方式。调用层根据 provider 决定是否注入 `thinking: disabled` 参数。

**API Key 绝不能硬编码**。存 `EncryptedSharedPreferences`，日志与错误信息中脱敏。

### 空状态与视觉噪音

- **砍掉独立空状态页**：空状态是列表页的 `if (list.isEmpty())` 分支，不是独立页面。
- **默认状态不显示 chip**：待深化的卡片不标"待深化"——用户扫一眼就知道哪些没聊过。只有非默认状态（追问中/待成文/已过时/已放弃）才显示标签。
- **保留回收站**：取消归档后，删除不可逆会让用户不敢删任何东西。30 天软删除，支持恢复。

### 全局文案风格

既然 AI 是抬杠式，App 自身文案也保持一致。温柔鼓励的 UI 配抬杠的 AI 会显得精神分裂。

| 场景 | 常规文案（不用） | 抬杠式文案（用） |
|---|---|---|
| 无待深化 | 快去记录你的第一条想法吧！ | 想法不记下来，跟没想过一样 |
| 未深化提醒 | 你有 4 条待深化的内容 | 记了 15 条，4 条没被追问过——想法放久了会馊 |
| 追问完成 | 太棒了！你完成了一次深度思考！ | 5 轮聊完了。你自己把它想通的，不是我 |
| 素材不足 | 内容太少，无法生成 | 你聊得太少了，这篇现在写不长 |
| 空思考库 | 暂无文章 | 追问完一条想法，文章会自动出现在这里 |

## Testing Decisions

### 核心测试缝隙

> **✅ 已定稿** —— 用户已确认采用本方案（2026-10-14）

**唯一的主缝隙：AI 服务接口。**

所有 AI 交互都通过 `AiService` 接口。测试时注入 `FakeAiService`（可预设返回内容、控制流式速度、模拟失败），即可在完全确定性的条件下测试上层全部逻辑——不需要真实 API、不消耗 token、不产生网络依赖。

这是最高位置的缝隙，因为它同时覆盖了追问、成文、转选题三个阶段，而这三个阶段恰恰是最难测的部分（输出不确定、有流式、依赖模型行为）。

补充缝隙（都是这个主缝隙的下游，不需要单独设计）：
- **派生状态计算**——纯函数，从 note/deepening/article/script 算出 8 个状态之一。最容易测，也最容易错。
- **手势判定**——输入 dx/dy，输出「右滑标记/左滑移回/无动作」。

#### FakeAiService 需要支持的能力

| 能力 | 用途 |
|---|---|
| 预设脚本化返回 | 按调用次序返回预设的追问问题，构造确定的对话流程 |
| 流式速度控制 | 把打字机速度调到极快（测试不等待）或极慢（测试跳过逻辑） |
| 失败模拟 | 模拟超时、429、401、余额不足，验证降级与错误归因 |
| 素材不足模拟 | 返回空 `content`，验证"拒绝成稿"而非出注水文章 |
| 提前收尾模拟 | 在第 3 轮返回收束信号，验证"聊透了 · 3 轮"文案 |
| 请求捕获 | 断言发给模型的 prompt 内容（验证权限边界未被破坏） |

最后一项尤其重要：它让「追问 prompt 里不能出现给答案的措辞」这条规则变成可自动验证的断言，防止后续重构悄悄破坏核心设计。

### AiService 接口的形状要求

为了让 FakeAiService 能完整替代真实实现，接口需要满足：

- 追问与成文**分开**——两者的权限边界不同，不能用同一个方法加参数区分
- 流式输出与一次性输出**分开成两个方法**——追问需要流式（打字机效果），成文不需要
- 错误以类型区分而非字符串——调用方需要按类型决定降级行为

概念形状：
```
interface AiService {
  // 追问：流式，每轮一个问题
  fun streamQuestion(history, note): Flow<String>

  // 成文：一次性，可能返回"素材不足"
  suspend fun composeArticle(history): ComposeResult

  // 转选题：一次性，多个角度
  suspend fun deriveAngles(article): List<Angle>
}
```

**分开是必须的**——如果追问和成文共用一个 `chat(prompt)` 方法，那么"追问不给答案"这条规则就只能靠 prompt 里的措辞来保证，而没有任何结构上的保障。分成不同方法后，追问方法在类型上就不可能返回一段总结。

### 什么算好测试

**只测外部行为，不测实现细节。**

具体到本项目：

| ✅ 该测 | ❌ 不该测 |
|---|---|
| 走完 5 轮追问后，收尾卡显示"5 轮追问完成" | `askQ()` 内部调用了几次 `setInterval` |
| 素材不足时 AI 返回拒绝，成稿页显示"你聊得太少了" | Prompt 字符串的精确内容 |
| 右滑后选题卡显示「✓ 已拍摄 · 今天」 | 手势监听的 event handler 数量 |
| 编辑文章后 `mine_count` 保持不变（还是同一篇） | 编辑框用了 textarea 还是 contenteditable |
| 「来源」视图标注的 AI 段数 = 总段数 − mine_count | 标注元素的 class 名 |
| 左滑后文章仍在思考库里 | 抽屉组件的状态管理方式 |

### 各模块测试要点

**记录层**
- 标题留空时自动截取正文前 18 字
- 正文为空时保存被拒绝并提示
- 保存后不跳转任何 AI 相关页面
- 草稿在切后台后恢复

**追问层**
- 每轮只发送一个问题（检查 FakeAi 收到的请求）
- 追问 prompt 中不含"你可以这样回答"这类给答案的措辞
- 进度点在发送后点亮（发送前 dot 状态为 `now`，发送后为 `done`）
- 5 轮答满后自动进入收尾卡，不再问第 6 轮
- 提前收尾时文案是「聊透了 · N 轮」而非「还剩 N 轮」
- 历史折叠行显示的是用户原话摘录，不是 AI 生成的摘要
- 打字动画期间输入框可用（发送按钮禁用但输入框不禁用）
- 点击气泡跳过动画

**成文层**
- 素材不足时 AI 返回空 content，UI 显示拒绝文案而非空文章
- 追问 < 3 轮时收尾卡显示预警
- 编辑保存后 `id` 不变、`parent_note_id` 不变（还是同一篇）
- 「来源」视图的 AI 段数与 `mine_count` 一致
- 成文 prompt 明确包含"可以补充论证"且包含"不改变观点立场"

**思考库层**
- 选题被左滑移回后，文章仍在列表中
- 同一篇文章可创建多条 script，原有的不受影响

**选题层**
- 右滑标记已拍摄后，`shot == true` 且 `shot_date` 有值
- 左滑移回后 `parked == true`，`shot` 不变
- 撤销条 7 秒后自动消失
- 选角度后第 1 段写作目标已替换
- 骨架 phrases 是意群短语结构（每条 ≥ 4 字且含语法成分）

**派生状态**
- 一条 note 同时有 script 和 child_note 时，状态判定为「已拍摄」（优先级 1 > 2）
- 全部 8 种状态的组合场景各一个用例

**服务商配置**
- 选 DeepSeek 自动填入正确 base_url 和 `deepseek-flash`
- 选 MiMo 自动填入 `mimo-v2.6-pro`
- 选 MiMo 时请求体**必须含** `thinking: {"type":"disabled"}`
- 选 DeepSeek + flash 时请求体**不含** thinking 参数
- SSE 解析器遇到 `: keep-alive` 注释帧不报错
- 测试连接的错误归因映射：401 → Key 无效，404 → 模型名不存在，余额不足，端点不匹配

**统计层**
- 漏斗用全局口径计算（每段/累计总数），不是相邻转化率
- 中间态说明行的数字与实际待处理数一致
- 「已开拍但未标记」的提醒条数正确

## Further Notes

### 这个产品最可能失败的地方

**MVP 阶段，用户标记「已拍摄」之后，App 不给任何"我这次表达得好不好"的反馈。**

整个价值链是：记录 → 想清楚 → 写成文章 → 转选题 → 拍完 → 结束。唯一回报是完成感（连续天数），而非能力提升的证据。

这在冷启动期是可行的（习惯先于反馈），但如果用户拍到第 5-7 天开始流失，几乎必然是因为"拍了但不知道有没有变好"。

因此建议 P2 把「拍摄后隔天弹一条回放对比」排在「质量评分」之前——开发成本更低、感知价值更高。

### 两个需要在实现时保持警惕的诱惑

**1. 让成文阶段的 AI 越界。**
一旦发现 AI 写的文章"读起来更好"，很可能会想在追问阶段也让它给点建议。那会摧毁整个产品的核心价值。用户获得的是一篇好文章，还是一次真实的思考过程？这两件事不可兼得。

**2. 给追问加"还剩 N 轮"。**
进度压力看起来是合理的用户引导，但会让用户为了尽快结束而敷衍回答——而追问的全部价值都依赖于用户真的在想。

### 已验证的原型

交互原型已完成并经多轮决策迭代，包含：五格导航（含居中加号）、5 轮追问对话模拟（可实际打字）、文章阅读与编辑、「来源」标注视图、换角度弹窗、选题左右滑、统计嵌套漏斗、设置页服务商配置与测试连接。

原型中沉淀了两处可直接复用的表达（比散文更精确地编码了决策）：

**派生状态优先级判定**
```
1 已拍摄     shot != null
2 已过时     存在 child 且 child 状态 ∈ {追问中,待成文,已成文,已成选题}
3 已成选题   存在 script
4 已成文章   article 存在 && deepening.completed
5 待成文     deepening.completed && 无 article
6 追问中     deepening.active
7 待深化     无 deepening
8 已放弃     deepening.abandoned
```

**轮次状态文案规范**
```
轮次 1-4  →  "第 N 轮 · 最多 5 轮"
轮次 5    →  "最后一轮"
提前收尾  →  "AI 判断这里已经聊透了 · N 轮"
禁用      →  "还剩 N 轮"（倒计时会诱发敷衍作答）
```

### 尚未验证的假设

- 5 轮追问是否足够。想清楚一件事通常需要更多轮，但上限越高完成率越低。原型里 AI 可提前收尾是缓解，但真实分布未知。
- 成文质量是否真的"逻辑清晰、语言优美"。这依赖模型能力，且 (c) 方案下质量波动更大。
- 用户是否真的会点「来源」视图。如果从不点，"个人思考资产"的定位会慢慢稀释。

### 实现起点

测试缝隙定稿为`AiService` 接口后，第一批代码的顺序建议如下：

1. **搭骨架** —— Gradle + Hilt + Room + Navigation + Compose，空壳可跑
2. **先写 `AiService` 接口和 `FakeAiService`** —— 在没有任何 UI 的情况下把三个阶段的服务层跑通，用测试把权限边界钉死
3. **派生状态计算 + 全组合测试** —— 纯函数，最容易错，先测掉
4. **再做 UI** —— 有了上面三层的测试兜底，UI 可以快速推进

这个顺序的用意是：**把最容易悄悄崩掉的部分（AI 权限边界、状态派生）放在还没有 UI 的时候测掉**。等UI 铺开之后再回头改这些规则，成本会高很多。

### 实现前必须先做的事

本机**尚未安装任何 Android 开发环境**：JDK、Android SDK、Android Studio、Gradle、Kotlin 五项全部缺失。

建议安装顺序与注意事项：

| 步骤 | 内容 | 注意 |
|---|---|---|
| 1 | JDK 17+ | AGP 8.x 硬性要求，JDK 17 或更高 |
| 2 | Android Studio | 会自带 JDK，也可单独装 |
| 3 | Android SDK | 需 API 35 +对应 Build Tools |
| 4 | 国内镜像源配置 | Gradle 与 SDK 都需配镜像，否则同步依赖会极慢或失败 |

磁盘空间：C 盘剩 47 GB / D 盘 101 GB，装工具链约需 15-20 GB，够用。
