# 2026-10-19（接续：换模型后的代码审核）

新模型接手项目，通读 README + 12 份工作记录 + 全部 58 个 Kotlin 文件，跑测试并做代码审核。

## 结果

- 审核前：276 条测试全绿，但**主链路其实是断的**
- 修复后：**286 条全绿**，APK 重新打包（`outputs/suiji-v0.7e.apk`）
- 报告：`outputs/随手记-代码审核报告-2026-10-19.md`

## 最关键的发现：追问的回答被丢掉

`DeepeningViewModel.send()` 里：

    nextRounds = rounds + Round(question = current.streaming, answer = userText)
    // 流结束后
    finalRounds = rounds.dropLast(1) + Round(question = streaming, answer = null)

`dropLast(1)` 删掉的正是刚落库的那句回答。

连锁后果：折叠区空白 → 进度点归 0 → 成文 `materialSize = 0` → **永远判素材不足拒稿**。
也就是说「AI 追问 → 成文章」在真机上从来没真正通过。

修法：`Round` = 一个问题 + 可选一个回答。回答写进最后一轮，下一问**追加**。

2. 续问传 `rounds = emptyList()`，上下文丢失 → 统一 `askQuestion(history)`

## 方法论

**状态类测试测「定义」，链路测试测「行为」。** 前 276 条全在测前者，
而三轮真机阻塞问题全在 ViewModel 层。新增 `DeepeningFlowTest` 用 FakeAiService + 内存 DAO

# V0.8：追问问不出来 + 追问方法学

## 真机反馈

「AI 追问无法进行下去，提不出问题来」。另问：追问是不是有几种方法学，
能否在设置里选择，每种对应不同提示词。

## 根因：追问请求从来没发过原始记录

`RealAiService.streamQuestion` 只发 `context.rounds`。
第一问时 rounds 为空 → 请求体里只剩一条 system message → 模型没有素材。

修法：`probeMessages()` 把 `originalNote` 固定成第一条 user 消息，
后续每轮都带（第四轮时这个锚点更重要）。

**做了反向验证**：临时把 `probeMessages(context)` 换回 `context.rounds`，
`RealAiServiceTest` 里两条立刻红，恢复后绿。证明测试不是空转。

## 追问方法学

`ProbeMethod` 四种：苏格拉底（默认）、连续五问、反方质询、还原场景。

**关键结构：共享禁区 + 差异化手法。**
`Prompts.probeSystem(method)` 只替换 `method.instruction`，
禁区（不给结论/建议/替代方案）不在方法里写——所以加第五种方法也不可能漏。
`ProbeMethodTest.禁区段落不因方法而变` 逐字比较四种方法的禁区段。

存储：`ProbeMethodStore` 接口 + `SharedPrefsProbeMethodStore`（普通 prefs，
不含敏感信息）。接口化是为了让 JVM 链路测试能塞内存实现。

`DeepeningContext.probeMethod` 携带方法，这样「设置选了哪种 → 请求里就是哪种」
能被断言，不依赖 Android 存储。

## 顺手修的两处

1. 模型输出收尾语（「我觉得你想清楚了」）会被当成又一个问题追加进轮次，
   界面停在等你回答而用户无从下口。改为：**每一轮都必须是问句，结束权归用户**。
2. 思考模式开关原来只对 MiMo 显示，但 deepseek-flash 不关思考时正文为空。
   改为所有预置服务商都显示，文案加上「追问不出字时先确认这里是打开的」。
   ViewModel 里补一句可执行提示，不再让用户面对空白。

## 版本

V0.8 / versionCode 8。308 条测试全绿（debug + release 各 308）。
新增 `ProbeMethodTest` 15 条、`RealAiServiceTest` +5、`DeepeningFlowTest` +3。

# V0.8.1：缺逗号的 400（真机第二轮反馈）

## 症状

装机后点「AI 追问」，第一问就报「出了点问题，具体原因看不出来」。
输入框灰着，placeholder 是「等一会儿…」——**看起来在转，其实已经停了**。

## 根因

`RequestBuilder.probe` 拼 messages 时漏了 system 后面的逗号：

```
"messages":[{system}{user}]   ← 非法 JSON
```

服务商返回 400。错在 App，不在用户的 key。

**`compose` 漏了同一个逗号**——所以「写成文章」从来没成功过。
以前没人走到那步，是因为追问先断了。

## 为什么 327 条测试没抓住

四个 builder 各拼各的 JSON，测试全用 `body.contains("...")`。
`contains` 对语法错误完全免疫：一个缺逗号的字符串照样包含所有关键字。

**教训：断言"包含某段文字"不等于断言"这是个合法请求"。**

## 修法

1. 四个入口共用 `RequestBuilder.chatBody` 一条拼接路径，逗号只写一次。
2. 新增 `ProbeRequestJsonTest`（11 条），测试自带极简 JSON 解析器
   （不引 org.json，unit test 里它是 stub），把每个 builder 的产出真解析一遍。
   **修复前 7 条红**，这就是有效性证明。
3. `ErrorKind.BAD_REQUEST` 单独一类，`TransportException` 带 `statusCode`+`detail`，
   `humanize` 附服务商 message。用户下次截图就能说清发生了什么。

## 另一条

标题下的五个小灰点删掉。用户直觉是对的：它什么也不说明，
而且「还剩几个」正是这版刻意不显示的——倒计时诱发敷衍作答。
`ProgressDots` 组件一并删除。方法名（苏格拉底式）留着，
它回答的是「我在设置里换的问法生效了吗」。

## 版本

V0.8.1 / versionCode 9。327 条全绿（debug + release 各 327）。

# V0.8.2：思考模式吃掉正文

## 症状

V0.8.1 装机后追问仍然失败，无法出现 AI 的问题。

## 判断

JSON 逗号是**确凿**的必然失败（测试证明 7 条红），修完还失败说明还有第二个原因。
查 DeepSeek 文档确认：模型名 `deepseek-flash` 正确、
`thinking:{"type":"disabled"}` 参数格式正确、**思考模式默认开启**。

于是最可能的一条是：思考模式开着 → 思维链先吃掉 `max_tokens` → 正文一个字都不来。

## 修法

1. **追问无条件关思考**：`probe(forceNoThinking = true)`，不看 `cfg.thinkingDisabled`。
   那个值取决于历史配置/用户点没点过/旧版本写了什么，太脆。
   一个「省时间」的选项不该有能力让核心功能整个失效。
   只对预置服务商生效，自定义不强塞（对面可能不认这个字段）。
2. `max_tokens` 200 → 1024，给正文留空间。
3. 设置页勾选框文案改为「关掉思考模式（只影响成文）」，说明追问固定不思考。

## 更重要的一层：空回复要能分三种

以前 SSE 里解析不出 content 的帧全被丢掉，三种故障长得一模一样：
- 只收到 reasoning_content（思考吃光了输出）
- 流里夹着 error 帧（额度/审核）← 以前完全被藏起来
- 服务商推空流

现在 `StreamAudit` 记账，流结束零正文就抛可归因的异常：
`THINKING_ONLY` / `STREAM_ERROR` / `NO_CONTENT`，各自不同话术。

**这层的价值不在修某个 bug，而在下次再坏时界面会自己说是哪种坏。**

V0.8.2 / versionCode 10。338 条全绿（debug + release 各 338）。
新增 `StreamAuditTest` 9 条。

# V0.8.3：追问通了，露出三个「依赖有数据」的 bug

## 关键进展

真机上第一次完整聊完三问三答。**追问链路确认走通。**
截图证据：标题下有三轮问答，最后一轮等待回答。

## 三个新暴露的问题

### 1. 详情页 `"已追问 $rounds 轮"`

`$rounds` 是 `List<Round>`，字符串模板照单全收 `toString()`，
整串 `[Round(question=..., answer=...)]` 打到屏幕上。
应为 `${rounds.size}`。

**这类 bug 编译器完全不管**——模板接受任何对象。
除了修插值，还给 `Round` 手写 `toString()` 兜底：
以后误插值时至少显示「问：… 答：…」。

### 2. 成文 messages 以 assistant 结尾

追问常停在「AI 刚问完、用户没答」。直接拍平 rounds →
最后一条是 assistant → `response_format: json_object` 要求结尾是 user，
否则模型顺着问题续写而不是成文。这是成文失败最可能的原因。

`composeMessages()` 末尾补一条用户指令。

### 3. `ComposeResult.Failed` 只有 4 个枚举，没地方放 detail

追问侧 V0.8.2 带了 detail，**成文侧整条链路都在丢原文**。
现在 `Failed(kind, detail)`，四个失败点各自带出线索：
HTTP 非 200 → 服务商原文；无 content → raw 前 300 字；
有 content 但无 paragraphs → **模型实际输出**；数组为空 → 原始数组。

## 版本

V0.8.3 / versionCode 11。343 条全绿。RealAiServiceTest +5。
