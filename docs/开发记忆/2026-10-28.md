## ⚠️ 迁移顺序不能换（这条是用脑子换来的）

`DROP TABLE article` 在开启外键时会触发级联，把 `script` 全删掉且不报错。
所以必须 **先重建 script（去掉指向 article 的外键）→ 再重建 article → 最后 trashed**。

如果按直觉先改 article，用户的选题会静默消失。

## 两个测试当场抓住的不一致

1. **trashed 主键生成规则不一致**：迁移 SQL 写 `'tr_' || noteId` → `tr_n2`，
   而 `IdeaRepository.moveToTrash` 用 `"tr_${type}_${resourceId}"` → `tr_note_n2`。
   已统一成后者。
2. **「删记录后 note 表应为 0 条」是错的**：回收站里的记录只是被标记，
   行还在 note 表里。删 n1 后应是 1 条（n2 还在回收站）。

### 两条踩过的语义坑（别再犯）

**1. `hasSource` 不能用 `sourceNoteId != null` 判断。**
`sourceNoteId` 是普通列（已去外键），记录删完之后它还是非空字符串，
界面会一直说「出处还在」，点进去是空白页。必须由仓库层判断 note 是否真存在。
`ArticleView` 现在有 `sourceNoteExists` + `hadSource` 两个字段：
`hadSource` 区分「本来就没出处」和「出处被删了」——后者才配说「原始记录已删除」。

**2. `assemble()` 与 `findArticle()` 对「进了回收站的记录」必须给同一个答案。**
前者用 `observeActive()` 的 id 集合（已排回收站），后者原本用 `noteDao.exists`
（含回收站）→ 同一条文章在两个页面显示不同。已统一成 `exists` 语义（含回收站），
因为回收站里的记录理论上还能恢复，说「已删除」太早。

### 崩溃：`padding(start = 负值)`

`TopicScreen` 左滑用 `Modifier.padding(start = dragX.dp)`，dragX 为负直接抛
`IllegalArgumentException`。**这条路径从来没走通过**——因为以前没人真去左滑。
换成 `Modifier.offset { IntOffset(...) }`。
Compose 布局错在 JVM 单测里跑不到，加了 `SwipeCardLayoutTest` 读源码扫
`padding` + `coerceIn(-` 的组合（先剥注释再扫，否则自己的注释会命中）。
反向验证过：改回 `padding` 两条都红。

### 统计口径

`composeRate` / `shotRate` 分母为零时返回 `null`，界面显示「—」。
返回 0 会让「一条记录都没写」看着像「写了不少一篇没成」。
0% 时连 8dp 空槽也不画——那条灰线会被看成分割线。

- `LibraryJson` 编解码**一起写**。导入留到下一版，但格式现在就得验证可逆——

- 两条写入路径：API 29+ 走 MediaStore（不要权限），26–28 写文件 +

- 校验手法：用 python 的 `json.load` 独立验一遍设备上真实导出的文件。
  `body.contains(...)` 那类断言对语法错误完全免疫（V0.8.1 就是这么栽的）。

### 文本选择：两种需求，两套机制

- 只读复制 → `SelectionContainer`（原生 Copy/Select all）。不自定义菜单。
- 捡一句用 → **只有追问页原始记录给**。Compose 的 SelectionContainer
  **不把选中内容交出来**（TextToolbar 只有位置），唯一的路是只读
  `BasicTextField` + 从 `value.selection` 切子串。
- 预览那行必须念出**将要插入的原文**，不能只报字数。
  字数不可核对，用户点下去才发现收错了。
- `pickedText` 抽成纯函数，7 条测试守着「拖反方向 / 没选 / 区间越界」
  三种情况都返回空串。（注意：`TextRange(-5, ...)` 构造时就抛异常，
  负数这头不用管。）
